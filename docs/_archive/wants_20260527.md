# wants: 公開ショーケース (<slug>)

  ## 目的
  - (a) 運用中のマイクロサービス群を一般公開し、リアルタイム稼働状況で「実際に動いている」信頼を示す（ポートフォリオ）
  - (b) AI コンサル案件の lead-gen（「AI 駆動開発で速く作る/コンサル承ります」）

  ## 構成要素
  1. 稼働サービス一覧: service-hub の `GET /api/public/status`(安全サブセット: slug/表示名/URL/up・down/稼働開始日) を fetch
  してリアルタイム表示。各サービスへのリンク。財務/コスト/離脱率など内部指標は出さない。
  2. LP（ランディングページ）: 何者か（週1ペースで AI 駆動開発、稼働中のサービス群）/ 提供価値 / コンサルの打ち出し（できること・進め方）。
  3. 問い合わせフォーム: 「AI コンサル案件承ります」。スパム対策込み（honeypot + rate limit、必要なら captcha）。送信は通知（メール or Slack）。フォーム送信値は最小限・PII 配慮。

  ## アーキテクチャ（確定済の前提）
  - service-hub とは別サービス（別 repo / 別デプロイ / 別サブドメイン）。HUB の財務データ・PaaS トークンと同居しない。
  - HUB の public status API のみ read-only 消費。稼働情報はキャッシュして HUB を叩きすぎない。
  - 一般公開（認証なし）。サブドメ運用 `<slug>.<domain>`（release §3.2）、告知は /flow:promote。

  ## 非機能
  - SEO / OGP（共有・検索される前提）、初回表示の軽さ。
  - 撤退容易性（O29: サブドメ DNS 1行削除）。
  - コピーは O38 準拠（一般向け・技術用語を避ける）、コンサル文面は射幸心を煽らない（charter §2.2）。

  ## 収益
  - コンサル lead-gen。ideate charter の収益モデル制約 / 価値観と整合を確認。

  ## 依存
  - service-hub に `GET /api/public/status`（安全サブセット）を1本追加する必要あり（HUB 側は別途 /flow:revise、本サービスの concept で contract を確定）。

  新規マイクロサービス「<slug>」(例: shipyard) を立ち上げる。/flow:concept から始めて。

  【これは何】運用中の自作マイクロサービス群を一般公開するショーケース + AI コンサル lead-gen の LP。週1ペースで AI
  駆動開発しているメイカーの「実際に動いているサービス一覧」を見せ、信頼を作り、コンサル問い合わせを受ける。

  【構成】(1) 稼働サービス一覧（リアルタイム up/down）、(2) LP（提供価値 + コンサルの打ち出し）、(3) 問い合わせフォーム「AI コンサル案件承ります」(スパム対策 + 通知)。

  【重要な前提・既決事項】
  - これは別サービス「service-hub」(内部観測 HUB、非公開・Clerk gate) とは切り分けた公開サービス。HUB の財務/コスト/離脱率データや PaaS トークンとは絶対に同居・公開しない。
  - 稼働情報は HUB が出す公開 API `GET /api/public/status`（安全サブセットのみ: slug/表示名/URL/up・down/稼働開始日）を read-only 消費して表示する。内部指標は受け取らない。HUB 側のこの
  API 追加は別タスク（service-hub の /flow:revise）で、本サービスの concept でその contract（レスポンス形）を確定させたい。
  - 一般公開（認証なし）。既存ドメインのサブドメ運用 `<slug>.<domain>`。
  - SEO/OGP 対応、初回表示軽量、撤退容易（DNS 1行）。コピーは一般向け（技術用語回避）、コンサル文面は煽らない。
  - 収益はコンサル lead-gen。
